## 1. Masalah yang diperbaiki

Catatan klinis yang belum ditandatangani saat kunjungan ditutup terkunci sebagai `LockedUnsigned`.
Catatan itu tidak bisa ditandatangani lagi. Akibatnya berkas kunjungan tersebut mustahil dinyatakan
lengkap — syarat 1 `RM-DEC-045` menuntut setiap catatan sudah ditandatangani.

`RM-DEC-049` memutuskan jalan keluarnya: penulis asli (atau penggantinya yang sah) membuat
**addendum pengesahan** yang menyatakan isi catatan benar. Status catatan **tetap**
`LockedUnsigned` sebagai jejak jujur bahwa catatan tidak ditandatangani pada waktunya.

**Contoh:** dr. Rina menulis CPPT pukul 09.00 tetapi lupa menandatangani. Pasien pulang pukul
11.00, dan CPPT terkunci `LockedUnsigned`. Esok harinya dr. Rina membuat addendum pengesahan.
CPPT tetap `LockedUnsigned`, tetapi kini ada pernyataan sah dari penulisnya.

## 2. Proses bisnis

**Tujuan:** catatan `LockedUnsigned` dapat disahkan penulisnya tanpa mengubah status catatan.

**Pelaku:** penulis asli catatan. Bila penulis berhalangan: pengguna berizin
`ClinicalNoteAddendum : CreateAsSubstitute` lewat jalur `as-substitute`, dengan akun penulis
nonaktif atau penetapan berhalangan yang masih berlaku (`RM-DEC-004`, `RM-DEC-020`).

**Langkah:**

1. Pengguna mengirim addendum dengan `purpose = Attestation` (nilai `2`) ke endpoint addendum yang sudah ada.
2. Sistem memeriksa status catatan: harus `LockedUnsigned`.
3. Sistem memeriksa belum ada pengesahan lain pada catatan itu.
4. Sistem memeriksa pembuatnya: penulis asli, atau pengganti yang sah.
5. Addendum tersimpan dan langsung ditandatangani — pembuatan sama dengan penandatanganan.
6. Status catatan tidak berubah; penghitung addendum bertambah satu.

**Aturan yang berlaku:**

| Keadaan | Hasil |
| --- | --- |
| Catatan `LockedUnsigned`, penulis asli | Tersimpan `201`; status tetap `LockedUnsigned` |
| Catatan `Signed`, `Draft`, atau `Cancelled` | `409` — "Pengesahan hanya untuk catatan yang terkunci tanpa tanda tangan." (`VAL-RM-A01`) |
| Sudah ada pengesahan | `409` — "Catatan ini sudah disahkan sebelumnya." (`VAL-RM-A02`) |
| Bukan penulis, tanpa jalur pengganti | `403` — "Hanya penulis catatan yang dapat menambahkan koreksi." (pesan addendum yang sudah ada, `VAL-RM-A03`) |
| Pengganti dengan penetapan berhalangan berlaku | Tersimpan, bertanda `isSubstituteAuthor` |
| Koreksi sesudah pengesahan | Tetap boleh — batas satu hanya berlaku untuk pengesahan |
| Permintaan tanpa `purpose` | Addendum koreksi seperti sebelumnya |
| `purpose` di luar enum | `400` — "Maksud addendum tidak dikenal." |

**Jalur tidak normal — dua pengesahan bersamaan.** Keduanya lolos pemeriksaan langkah 3, lalu
index unik terfilter di PostgreSQL menolak salah satunya. Yang ditolak dijawab `409` `VAL-RM-A02`
dan tidak ada yang tersimpan setengah. Bila tabrakan ternyata bukan karena pengesahan lain
(misalnya nomor urut kembar dengan koreksi serentak), galatnya diteruskan seperti perilaku addendum
sebelum task ini.

## 4. Dokumentasi endpoint

#### Health Services / Medical Record Management / Clinical Note Addendum

Base URL `api/v1/health-services/medical-record-management/clinical-note-addendums`

| Method | Path | Perubahan | Hak akses |
| --- | --- | --- | --- |
| `POST` | `/by-document/{documentKind}/{documentId}` | Request menerima `purpose`: `1` `Correction` (bawaan), `2` `Attestation` | `ClinicalNoteAddendum : Create` |
| `POST` | `/by-document/{documentKind}/{documentId}/as-substitute` | Sama | `ClinicalNoteAddendum : CreateAsSubstitute` |
| `GET` | `/by-document/{documentKind}/{documentId}` | Respons menambah `purpose` per addendum | `ClinicalNoteAddendum : Read` |

Contoh permintaan pengesahan:

```json
{
  "addendumText": "Isi catatan ini benar sebagaimana tertulis.",
  "correctionReason": "Tidak sempat ditandatangani sebelum pasien pulang",
  "purpose": 2
}
```

Kode status baru: `409` (`VAL-RM-A01`, `A02`).
